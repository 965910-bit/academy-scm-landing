# WMS: проверка переходов и сохранения запасов

Автор: Герасимов Дмитрий Сергеевич. Версия 0.31.0 от 2026-11-19. Все данные вымышлены. Вводный последовательный симулятор, не промышленная WMS и не реализация GS1/EPCIS. Предметная, правовая, ответная экспертизы и апробация не выполнены. Лицензию распространения собственных материалов утверждает правообладатель; внешние права и объем чтения источника указаны в курсе.

## Запуск

Рядом сохранить `warehouse-stock.csv`, `warehouse-orders.csv`, `warehouse-events.json`, `warehouse-flow-lab.py`, `wms-transition-card.csv` и инструкцию. Python3 со стандартной библиотекой, без сети/пакетов/аккаунтов/рабочих данных:

```text
python3 warehouse-flow-lab.py --case wms
python3 warehouse-flow-lab.py --case wms --directory "папка сценария"
```

Бумажная таблица переходов равноправна для учебного разбора. Каждый запуск начинает с исходного CSV, а не продолжает прошлый. Данные/seen/журнал в памяти теряются после процесса. Никаких записей в исходник или реальных операций. Вывод сохранять только под новым именем. `--order` влияет только на статический план `--case picking`; WMS использует order_id самих событий. `--case all` показывает оба независимых расчета с исходного состояния.

**Два типа отказа:** неверный CSV/синтаксис JSON/дублирующийся ключ JSON/неправильный контейнер списка →код 2, stderr, пустой stdout. Валидный список с неверными командами →код 0 и JSON с `accepted=false` по таким командам. Бизнес-отказ —ожидаемый результат, не сбой установки. Запасы не меняются, но попытка отражается в результатах.

## Контракт и состояния

Stock: одна уникальная ячейка с одним SKU/lot/expiry, целым units0..1000000 и статусом available/quarantine. Orders: уникальный line_id,order_id,sku,положительное units; повтор товара в разных позициях суммируется. Даты строго YYYY-MM-DD. Таблицы 1..1000 строк; контроль после чтения не защищает от огромных враждебных файлов. Срез 19.11.2026, порог срока 22.11 включительно; FEFO по сроку и коду ячейки, не по времени поступления/расстоянию.

`on_hand` —записанное наличие. `holds` —резерв, включающий и еще не отобранное, и уже подтвержденное picked. Новый свободный запас=допустимое on_hand−все активные резервы. Pick не уменьшает on_hand и не вычитает резерв второй раз. Ship после полного pick уменьшает on_hand на резерв один раз и удаляет hold.

| Переход | Условие | Изменение |
| --- | --- | --- |
| reserve | Заказ известен, не терминален, еще не зарезервирован, хватает всех SKU | hold целого заказа, on_hand неизменен |
| pick | Есть hold, совпали bin/SKU/lot, положительное количество≤неподтвержденного остатка, запас допустим | Увеличение picked внутри hold |
| ship | Все строки полностью picked, запас допустим | Наличие минус резерв, hold удален, shipped |
| cancel | Есть hold, ни одной picked единицы | hold удален, наличие неизменно, cancelled |
| Действие после shipped/cancelled | Запрещено | Бизнес-состояние неизменно |
| cancel после pick | Запрещено | Нужен отдельный физический put-back/контроль, не реализован |

Инварианты по каждой ячейке:0≤сумма резервов≤наличие; по строке 0≤picked≤reserved. Прежде чем применить команду, состояние копируется; при ValueError бизнес-состояние восстанавливается. Это **не транзакцияБД/проверка конкуренции/долговечности**. Возврат на хранение, частичная отгрузка, изменение статуса, приемка, списание, корректировка и переоткрытие не реализованы.

## Формат события и повторы

Объект reserve/ship/cancel имеет ровно `event_id`, `action`, `order_id` (непустые строки). Pick дополнительно ровно `bin_id`, `sku`, `lot`, `units`; units —числовой текст, например `"6"`, не JSON-число 6. Неизвестные поля/команды, реквизиты и превышение количества отвергаются. JSON —список 1..1000 объектов/попыток; неверный объект в корректном списке регистрируется как отказ команды, не успешная операция.

После корректного нового event_id он попадает в seen даже при бизнес-отказе. Повтор ID отвергается, **не идемпотентный успех**. Исправление после отказа требует нового ID; нового ID недостаточно для обхода ограничений/терминального статуса. При отказе запас/holds/terminal неизменны, но аудит попытки существует. Здесь seen и журнал не сохранены на диске, поэтому межпроцессных/сетевых гарантий нет.

## Независимый эталон 12 команд

Начальное наличие 26: A01=6,A02=8,Q01=3,B01=5,B02=4. Допустимо 14A+5B=19. O01 нужно 10A+4B; O02 нужно 5A.

| Событие | Результат | Обоснование |
| --- | --- | --- |
| E01reserveO01 | Принято | Резерв 6A01+4A02+4B01=14, свободно 4A+1B |
| E02reserveO02 | Отказ | Нужно 5A, свободно 4A: дефицит 1; никакого частичного holdO02 |
| E03shipO01 | Отказ | Еще нет полного отбора |
| E04pickA01/SKU-B/L01/6 | Отказ | Неверный SKU, ожидается SKU-A |
| E05pickA01/SKU-A/L01/6 | Принято | Подтверждены 6 внутри резерва; наличие 26 |
| E06cancelO01 | Отказ | Уже есть picked; нельзя автоматически «вернуть» товар |
| E07pickA02/SKU-A/L02/4 | Принято | Подтверждены 4 |
| E08pickB01/SKU-B/L03/4 | Принято | Все 14 подтверждены |
| E09shipO01 | Принято | Единственное уменьшение наличия на 14 |
| E10shipO01 | Отказ | Терминальное shipped |
| E11cancelO01 | Отказ | Терминальное shipped |
| Повтор E09shipO01 | Отказ | ID уже использован; повторного эффекта нет |

Принято 5, отвергнуто 7. Итог наличие 26−14=12: A01=0,A02=4,Q01=3,B01=1,B02=4. Holds пуст, O01shipped, O02 не зарезервирован. Карантин 3 и истекший срок 4 остаются в наличии, не доступны. Допустимо 4A+1B=5. Все 7 отказов должны иметь `inventory_unchanged=true`; независимая проверка сравнивает снимки, а не только этот флаг.

## Отдельные ветки на чистом экземпляре

Создавать копии исходного JSON и начинать с исходного CSV. Не редактировать историю ради красивого результата.

1. Только reserveO01(E01)→cancelO01 с новым ID до любого pick: оба приняты, наличие 26/holds0/свободно 19, terminalcancelled. Повтор reserve того же O01 с новым ID отвергается по терминальному статусу.
2. ReserveO01→ship до pick: второй отказ, резерв 14 и наличие 26 остаются. Это не частичная отгрузка.
3. ReserveO01→pickA01/SKU-A/L01/7: второй отказ, потому что по A01 зарезервировано 6; picked остается 0.
4. ReserveO01→pickA01/SKU-A/неверный lot/6: отказ, партия не совпала. Не подменять lot в исходнике.
5. Повторить отказавшее E02 с тем же ID —повтор отклонен, даже если вы изменили объем. Чтобы исследовать иное условие, новая версия/новый ID/подтвержденная потребность; не выдавать это за реальное разрешение.
6. После успешной отгрузки на отдельном экземпляре попытаться еще раз ship с новым ID: терминальный запрет, второй раз 14 не списываются.

Для работы через Python импорт допустим `importlib.util.spec_from_file_location`; `load(stock_rows,order_rows)` создает словари, `Warehouse(stock,orders)` независимый экземпляр, `apply(event)` возвращает результат, `snapshot()` глубокую копию бизнес-состояния. `seen` не часть складского баланса. Программа не защищает от произвольного внешнего изменения ее внутренних словарей —это не серверный API.

## Приемочный пакет и 120 минут практики

15 минут —контракт/таблица состояний;30 —бумажная таблица 12 событий;20 —код/сверка снимков/ошибки входа;20 —отдельные ветки;20 —разбор ниже;15 —итог/версии/границы приемки. Время рекомендательное, перерывы и дополнительное время допустимы.

Разбор 20 минут: владелец требует «отменить после pick, чтобы свободный остаток появился сразу» и «запустить рабочую WMS, потому что тест зеленый». Проверяющий объясняет физический возврат/состояния и предел модели.4 минуты подготовки,5 разговора,4 наблюдения по конкретным доказательствам,4 исправления/повторного объяснения,3 следующего шага/роли/критерия. Письменная альтернатива разрешена, но живое взаимодействие не считается проверенным. Реальные данные/терминал/личные истории/запись голоса не нужны.

Сдать исходники/версии, контракт, таблицу результатов, независимый конечный баланс, снимки отказов, отдельную отмену до pick, первую/повторную записки и список неиспытанного: права, гонки, сбои, интеграции, оборудование, физическая приемка. P1 —состояния/числа;P2 —резерв/неизменность;P3 —переходы/баланс;P4 —протокол/границы. Каждый P:0 нет/неверно,1 существенные пробелы,2 малый пробел,3 полно. Q имеют индивидуальные рубрики 0/1/2; максимум 24, ориентир 18 без критических ошибок, не аттестация. Ролевой разбор не добавляет баллы.
