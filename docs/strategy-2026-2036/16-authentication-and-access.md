# Вход по ФИО, учётные записи и административный доступ

Основатель и разработчик проекта «Академия SCM» — **Герасимов Дмитрий Сергеевич**. Атрибуция по поручению основателя; сторонние источники сохраняют своих авторов.

Дата изменения: 19.11.2026. Этот документ заменяет прежние утверждения о возможности войти простым выбором роли. Переключатель роли на форме входа удалён. Старые клиентские списки пользователей/паролей удалены; прежние страницы входа и dashboard ведут в единый кабинет.

## 1. Что реализовано

- Node.js HTTP-сервис с SQLite на диске. База, сессии и аудит не коммитятся и не обслуживаются статическим маршрутизатором.
- Вход: полное ФИО и пароль. Пробелы схлопываются, регистр игнорируется, используется Unicode NFKC. `ё` не заменяется на `е`. Совпадающие нормализованные ФИО отклоняются: нужно согласовать различимый вариант с владельцем, а не угадывать по паролю.
- Роли: администратор, приёмная комиссия, абитуриент, слушатель, преподаватель, работодатель. Роль задаёт уполномоченный сотрудник, не пользователь на входе.
- Администратор создаёт аккаунты всех ролей. Приёмная комиссия создаёт и обслуживает только абитуриентов и слушателей, не видит остальные аккаунты через API и не выдаёт административные полномочия.
- Пароли генерируются криптографически стойко (18 случайных байт, base64url), показываются один раз после создания/сброса. В базе — salt + scrypt, не открытый пароль. Обязательна смена при первом входе/сбросе.
- Сессия: случайный токен, в БД только SHA-256 токена, cookie HttpOnly, SameSite=Strict, Secure по умолчанию; срок 8 часов. Выход, сброс пароля и блокировка отзывают соответствующие сессии. Смена пароля завершает остальные сессии владельца.
- Изменяющие запросы требуют совпадающего Origin и JSON. Нет CORS-доступа извне. Вход ограничивается по сочетанию IP/ФИО и IP: после 10 неудачных попыток временная блокировка на 15 минут. Эта защита локальна одному процессу; для нескольких экземпляров нужен общий limiter.

Список ролей в административной форме — назначение прав при создании, не свободный вход под любой ролью. Скрытая кнопка не считается защитой: ограничения управления аккаунтами проверяет сервер.

### Что здесь может пойти не так

- ФИО совпадут или изменятся: необходим регламент различения/изменения; самостоятельное переименование пока не реализовано.
- Временный пароль перешлют в общий чат: передавать отдельным защищённым каналом и сразу заменить.
- Обратный прокси объединит клиентов под одним IP: настройку ограничения частоты и доверенных прокси нужно проверить на хостинге.

## 2. Администратор открывает кабинет без изменения пароля владельца

В разделе «Пользователи и права» есть действие «Открыть кабинет без смены пароля». Сессия остаётся административной; сервер разрешает администратору загрузить и сохранить выбранное рабочее пространство. В интерфейсе видны имя владельца, режим административного доступа и возврат к управлению. Открытие и сохранение фиксируются в аудите с ID настоящего администратора.

Это **не** проверка пароля пользователя, не хранение его пароля и не массовая подмена учётных данных. Приёмная комиссия и остальные роли не могут запросить чужое пространство по `?user=...`: сервер возвращает 403. Сброс пароля — отдельное подтверждаемое действие, которое завершает сессии и требует новой смены владельцем.

### Что здесь может пойти не так

- Администратор забудет, чей кабинет открыт: баннер должен сохраняться на всех его экранах.
- Человек перепутает открытие кабинета со сбросом: это разные кнопки, сброс требует подтверждения.
- Доступ администратора примут за возможность незаметных действий: события доступа и сохранения регистрируются с его ID.

## 3. Рабочие пространства и честная граница полномочий

Состояние учебных модулей хранится отдельно для каждой учётной записи в серверном workspace. Обычный пользователь получает/изменяет только своё пространство; администратор — любое. Сохранение имеет ревизию: при записи поверх изменённой версии сервер возвращает 409, а не молча затирает новую запись. Конфликт требует экспорта и повторного открытия. В интерфейсе есть статус подтверждения сервера и экспорт.

**Это первый серверный контур аккаунтов, а не завершённая многопользовательская LMS.** Внутренние «учебные профили» и группы старых тренажёров относятся к текущему workspace. Они не становятся аккаунтами автоматически и не дают доступ к чужим данным. Преподаватель пока не получает общий доступ к работам всех реальных слушателей, приёмная комиссия не получает общую очередь всех реальных заявлений. Их сквозные организационные процессы требуют отдельной модели назначений и адресатов, а не открытия всех workspace. Изменение обучающимся JSON своего workspace не меняет его серверную роль и не является официальным назначением/аттестацией/выдачей документа.

Публикация направлений также пока относится к workspace администратора, а не к глобальной конфигурации публичного сайта. Утверждение программ, реальные документы, ЭП, ФРДО, договоры и платежи этим изменением не включаются. Нельзя назвать данные произвольного учебного JSON официальным реестром академии.

Общее браузерное хранилище прежней версии не импортируется в новые аккаунты автоматически: невозможно определить владельца старых общих записей. Исторические данные не удаляются из браузера, но вход их не загружает. Для миграции нужен отдельный проверяемый процесс и экспорт прежнего состояния. Продуктовые DOM-тесты используют изолированный identity-double, а HTTP-тесты проверяют реальную границу авторизации.

### Что здесь может пойти не так

- Внутренний учебный профиль сочтут новой учётной записью: аккаунт создаётся только серверной операцией из панели.
- Локальные сценарии преподавания назовут сквозной LMS: общий учебный поток ещё не интегрирован с аккаунтами.
- Старое общее состояние импортируют в первый попавшийся аккаунт: автоматической миграции нет намеренно.

## 4. Развёртывание и первый администратор

Требуется Node.js с `node:sqlite` (проверено Node 22.22.3; в этой версии модуль имеет experimental warning), постоянный диск и HTTPS. **GitHub Pages и `python -m http.server` не исполняют API:** для кабинетов теперь нужен сервер. Публичные HTML-материалы продолжают читаться статически.

Из корня репозитория:

```sh
npm ci --prefix academy
# DATA_DIR должен быть на постоянном защищённом диске вне публикуемых файлов.
DATA_DIR=/secure/academy-data node server/server.cjs bootstrap "Фамилия Имя Отчество"
PUBLIC_ORIGIN=https://scm-news.online DATA_DIR=/secure/academy-data PORT=4173 node server/server.cjs
```

Команда bootstrap создаёт первого администратора только при отсутствии административных аккаунтов и выводит временный пароль один раз в терминал оператора. В чате, коде и публичном JSON нет заводских учётных данных. Нужно подставить действительное согласованное ФИО владельца; в этой поставке постоянный администратор не создан без его указания. При потере доступа потребуется отдельный контролируемый механизм восстановления; старый публичный reset-password не выдаёт пароль из браузера.

Secure-cookie включена по умолчанию. `COOKIE_SECURE=0` допустим только для локальных HTTP-тестов, не для внешнего развёртывания. `PUBLIC_ORIGIN` рекомендуется задавать явно; за прокси нужно проверить Host/X-Forwarded-Host и не доверять произвольным внешним заголовкам. Сервер слушает 0.0.0.0. БД по умолчанию в `.academy-data/`, каталог игнорируется Git; для production предпочтительно абсолютное расположение вне checkout. Приложение обслуживает только публичные пути, а не корень файловой системы, серверный код или тесты.

Перед реальными персональными данными нужны аудит безопасности, процесс выдачи доступа, правовые основания обработки, резервные копии с испытанием восстановления, шифрование/права инфраструктуры, мониторинг и ответственные. scrypt и cookie не являются полным подтверждением соответствия законодательству или требованиям ИБ. Внешний pentest не выполнялся. Аудит в SQLite не защищён от изменения администратором самого сервера; для регулируемых операций нужен отдельный неизменяемый журнал и сроки хранения.

### Что здесь может пойти не так

- Сайт останется на статическом хостинге: форма входа не сможет проверить credentials без API.
- БД запишется на временный диск: аккаунты потеряются после пересоздания контейнера.
- Терминальный вывод bootstrap сохранится в общедоступных логах: оператор должен контролировать доступ и немедленную смену пароля.

## 5. Сеть, офлайн и испытания

Публичная библиотека и каталог документов доступны из подготовленного пакета v10 без сети. Приватные ответы API не кэшируются service worker и не сохраняются приложением в общий localStorage. Новый вход, загрузка кабинета и подтверждение сохранения требуют сервера. Во время обрыва сети открытая работа остаётся в памяти вкладки; показана ошибка сохранения, доступен экспорт, закрытие предупреждается. Полноценная приватная офлайн-очередь с безопасной идентификацией и слиянием — отдельная задача, не обещанная этой поставкой. Это осознанная граница, а не причина сделать роли незащищёнными ради офлайна.

Проверено 74 автоматических теста: старые UI/worker/static сценарии с identity-double плюс реальные HTTP-тесты нормализации ФИО, смены временного пароля, ограничений ролей, изоляции, ревизий, административного чтения без изменения пароля, сброса, блокировки, выхода, Origin, ограничения попыток и запрета скачивания закрытых файлов. Новый Chromium smoke проверяет настоящий HTTP-вход, первую смену, создание/генерацию, открытие чужого кабинета администратором, сохранение после перезагрузки, выход и ширины 320/390/768. Он использует временную БД и синтетические аккаунты, которые удаляются после завершения; пароли не выводятся в отчёт.

Прежний браузерный сценарий свободного переключения ролей заменён — это больше не допустимый способ входа. Число DOM-тестов не является числом проверок безопасности: один HTTP-сценарий содержит несколько отдельных запросов. Не проверены production-прокси, режим нескольких процессов, нагрузка, доставка паролей, внешнее восстановление и полный аудит UI на приватность. Слова об официальных документах и неподключённых интеграциях не удаляются ради вида готовности.

### Что здесь может пойти не так

- Офлайн-оболочку примут за разрешение войти без сессии: приватная авторизация без сети не выполняется.
- Положительный локальный тест назовут готовностью к любой нагрузке: необходимы отдельные испытания развёртывания.
- Удаление надписей прежнего режима скроет реальные незавершённые процессы: ограничения документооборота и совместного обучения остаются явными.
