## 1. Схема и ограничения целостности

Реляционная модель задает сущности, ключи и связи. В database-transactions-lab.py: bins с bin_id, products с sku, stock с составным ключом (bin_id,sku), movements с уникальным movement_id. Начало: B1/SKU1=10, B2/SKU1=3, всего 13 единиц; две ячейки, один товар, журнал пуст. Строка stock — остаток товара в ячейке, строка movements — событие, а не текущий остаток.

NOT NULL запрещает отсутствие обязательного значения; PRIMARY KEY/уникальность — повтор ключа; FOREIGN KEY — ссылку на отсутствующую родительскую строку; CHECK — нарушение условия значения. Для stock проверяется целочисленный неотрицательный остаток, для movements — положительное количество и разные ячейки. Один внешний ключ без NOT NULL может разрешать NULL. Ограничения не подтверждают истинность фактического остатка.

SQLite foreign keys включаются и проверяются на каждом соединении до операции: PRAGMA foreign_keys=ON и ответ 1. Нельзя полагаться на значение по умолчанию или включать их посреди активной транзакции. Параметры связываются через ?, а не вставляются в SQL конкатенацией. Это разные меры: параметры не проверяют бизнес-правило, связи не дают прав доступа, комментарий не является ограничением БД.

## 2. Атомарная операция и явный откат

Перемещение M01 четырех единиц из B1 в B2 должно одновременно создать запись журнала, уменьшить источник и увеличить получатель. Последовательность: BEGIN IMMEDIATE → INSERT журнала → условный UPDATE источника → UPDATE получателя → COMMIT. Условие quantity>=? и результат rowcount=1 нужны, чтобы не уйти в минус и не принять отсутствующую строку за успех. После успеха 6/7, сумма 13, журнал содержит одну операцию.

Лабораторная операция M02 намеренно вызывает ошибку после вычитания 2 из B1, но до зачисления в B2. Обработчик явно выполняет ROLLBACK, если соединение еще в транзакции, затем возвращает ошибку. Остаются 6/7 и только M01, а не 4/7 и не запись M02. Ошибка одного оператора не является универсальной гарантией отката всей ранее выполненной части: поведение ошибок СУБД различается, поэтому рамка операции и обработка отката явные.

Попытки списать 7 при остатке 6, повторить movement_id=M01 или указать UNKNOWN-получателя отвергаются без изменения подтвержденного состояния. Дублирующийся ID здесь ошибка, а не идемпотентный успешный повтор. Для производственной идемпотентности нужны сравнение параметров и отдельный контракт повтора. Нельзя удалять журнал или создавать новый ID автоматически ради успеха.

## 3. Блокировка, копия и границы восстановления

SQLite допускает одновременно несколько читателей, но только одного писателя. В writer_lock_demo создается отдельная временная БД, два соединения с timeout=0: первое BEGIN IMMEDIATE, второе BEGIN IMMEDIATE получает SQLITE_BUSY. После ROLLBACK первого второе может начать и откатить транзакцию. Это последовательный управляемый эксперимент блокировки, не многопоточный или нагрузочный тест и не проверка бизнес-конкурентности всех СУБД.

Логическая копия создается sqlite3.backup в новую БД в памяти и сравнивается по состоянию stock/movements. PRAGMA foreign_key_check возвращает пустой список, integrity_check — ok. Это ограниченная проверка контрольного состояния. Не продемонстрированы сбой питания/диска, внешнее хранилище, шифрование, расписание/ретенция, независимое восстановление сервиса и RPO/RTO — цели допустимой потери данных и времени восстановления.

Версия схемы PRAGMA user_version=1 — маркер, не автоматическая миграция. Изменение схемы требует проекта миграции, резервной копии, проверки данных/совместимости и отката в инструкции передачи. Лаборатория создает только новую учебную схему; нельзя исполнять ее DDL поверх рабочей БД. Временные файлы удаляются после закрытия соединений, исходники не перезаписываются.

## 4. Приемка модели и передача

При ожидаемых отказах модели сценарий продолжает сверку; неожиданная ошибка лаборатории дает ненулевой код. Не маскируйте ошибку кодом 0 и не подменяйте результат несуществующим скриншотом.

Протокол содержит фактические версии Python/SQLite, версию схемы, исходные и конечные таблицы, состояние журнала, сумму 13, отказы/откат, проверки копии/целостности/блокировки и ограничения. ## Словарь

Транзакция: Явная единица согласованных изменений с коммитом или откатом.

Внешний ключ: Ограничение существования связанного родительского ключа.

CHECK: Условие значения, не общая проверка полномочий.

SQLITE_BUSY: Признак недоступности блокировки в проверяемом сценарии.

Логическая копия: Копия состояния БД, не полная процедура восстановления сервиса.

Идемпотентный повтор: Повтор с согласованным результатом без повторного бизнес-эффекта; здесь такой API не реализован.
