1. Остаток, резерв и событие — разные сущности

Warehouse Management System (WMS —система управления складом) связывает задания, состояние запасов и подтверждения операций. В нашем симуляторе on_hand —записанное наличие, holds —активные резервы заказов, picked —подтвержденный отбор внутри резерва. Свободно для нового резерва=допустимое on_hand−активные резервы; picked не вычитается второй раз, потому что остается частью резерва до отгрузки.

Исходное наличие 26 единиц: A01=6, A02=8, Q01=3, B01=5, B02=4. Допустимо для новых заказов только 14A и 5B;3A карантина и 4B с истекшим сроком не свободный запас. Срез 19.11.2026, минимум срока 22.11 включительно —учебное условие. Система не проверяет реальное физическое наличие, качество или полномочия человека.

Событие имеет event_id, action, order_id; pick дополнительно bin_id, sku, lot, units. Эти данные помогают проследить, к какому объекту/месту относится действие, но коды не являются валидированными GS1 идентификаторами. Обзор GS1 разделяет события и описывающие их данные; наш учебный JSON не реализация EPCIS. Реальные роли/доступы/журнал/обмен требуют отдельной системы и проверки.

2. Резерв целиком и сохранение инвариантов

Событие E01 резервирует O01: A01/L01=6, A02/L02=4, B01/L03=4 по FEFO. В памяти появляется резерв 14, но наличие остается 26. Следующий O02 требует 5A, а свободно 4A; E02 отклоняется с дефицитом 1. Сам по себе O02 на пустом от резервов исходнике выполним: отказ вызван уже действующим резервом, а не отсутствием товара вообще.

Инварианты: по каждой ячейке 0≤сумма резервов≤on_hand, по строке 0≤picked≤reserved. Планирование заказа целиком: если не хватает хотя бы одного SKU, не создается ни одна его строка резерва. Нельзя сначала «успешно» забрать один товар, а потом вернуть ошибку по другому без отмены всего изменения. В учебном классе состояние копируется до операции и восстанавливается при ValueError.

Это последовательная модель в одном процессе. Она не испытывает гонку двух пользователей, блокировку БД, потерю питания, сетевой повтор или долговечность журнала. Равенство остатка после отказа в такой модели не доказывает атомарность промышленной WMS. Для реального решения нужны транзакционное хранилище, права, ограничения, интеграции и независимые нагрузочные/сбойные испытания.

3. Отбор, отгрузка и запреты переходов

E03 пытается отгрузить O01 до полного отбора —отказ. E04 передает A01/SKU-B/L01/6 —отказ по товару. Затем E05 подтверждает A01/SKU-A/L01/6. E06 просит отменить уже частично отобранное —отказ: физический возврат в хранение не подтвержден, автоматическая отмена могла бы сделать тот же товар доступным повторно. Возврат требует отдельного безопасного процесса, которого симулятор не реализует.

E07 подтверждает 4A02, E08 —4B01. E09 отгружает полностью отобранный O01: только теперь наличие уменьшается на 14, активный резерв удаляется, заказ получает shipped. Итог A01=0, A02=4, Q01=3, B01=1, B02=4, всего 12; допустимый свободный запас 4A+1B=5. Карантин/истекший срок остались, не списаны и не отгружены.

E10 повторяет ship и E11 просит cancel после shipped —оба отказ. Повтор event_idE09 тоже отвергается: в этой модели нет идемпотентного успешного ответа на повтор. Даже неуспешная команда с корректным новым ID занимает его в наборе обработанных идентификаторов; повтор после исправления требует нового ID и отдельного решения. Наличие/резервы не меняются при отказе, но аудит попытки не равен отсутствию события.

4. Отмена до отбора, журнал и приемка

На отдельном чистом экземпляре reserveO01→cancelO01 без pick разрешено: наличие 26, holds пуст, O01cancelled; свободны 14A+5B. Терминальный cancelled также не переоткрывается автоматически. Это условие модели, не универсальный регламент всех WMS. Если нужны частичные отгрузки, корректировки, возвраты или переоткрытие, нужны отдельные состояния/полномочия/тесты, а не обход проверки.

Что может пойти не так: повторное сообщение дважды уменьшает остаток, wrongSKU подтверждается по одному адресу, резерв снимается без фактического возврата, отгрузка проходит по неполному отбору, журнал теряется при перезапуске. В нашем коде запас защищен только от описанных последовательных ошибок. Каждый запуск начинает с исходного CSV; база, долговечный аудит, сканер, авторизация и реальное перемещение отсутствуют.

Приемочный пакет содержит контракт данных/состояний, таблицу переходов, до/после каждой значимой команды, независимую сверку, запрещенные случаи и границы доказательства. Ошибки входной структуры завершают CLI кодом 2 безчастичного JSON; корректный файл событий с отвергнутыми командами выводит результаты и код 0. Операционный отказ —ожидаемый результат проверки, а не подтверждение готовности системы к эксплуатации.

  • Неверный товар/партия/количество подтверждены либо неполный заказ отгружен
  • Повторно списан запас/автоматически возвращен отобранный товар без процедуры

Q6. Как обрабатываются повтор ID и код завершения при ожидаемом отказе?

Ответ, основание и объяснение

Новый корректный ID занимается даже при бизнес-отказе. Повтор ID отклоняется, не дает идемпотентного успеха; исправленная новая попытка требует нового ID. Запасы при отказе неизменны, но аудит попытки остается. Валидный список команд с отказами→JSON/код 0; неверная структура CSV/JSON→stderr/код 2 безчастичного stdout. Это не сетевой протокол промышленной системы.

Нужно различать отказ команды, ошибку входа и семантику повторного сообщения.
