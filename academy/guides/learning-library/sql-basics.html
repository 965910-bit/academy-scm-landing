1. SELECT, WHERE и отсутствующее значение

SQL (Structured Query Language — язык структурированных запросов) описывает, какие данные нужны. В запросе SELECT order_id, amount_rub FROM orders WHERE status = 'paid' ORDER BY order_id перечислены поля, источник, условие и порядок вывода. Без ORDER BY порядок строк не гарантирован. Имена таблиц и полей должны соответствовать схеме.

Учебная orders содержит четыре заказа: 1, клиент 10, paid, 1000; 2, клиент 10, paid, 2000; 3, клиент 20, cancelled, 500; 4, клиент 30, paid, NULL. amount_rub — рубли без моделирования налогов. NULL означает неизвестную сумму, а не ноль. Условия amount_rub = NULL и amount_rub != NULL не являются проверкой отсутствия; используйте IS NULL и IS NOT NULL.

SELECT order_id FROM orders WHERE status = 'paid' AND amount_rub IS NULL вернет заказ 4. Его нельзя автоматически считать бесплатным. Для известной оплаченной суммы фильтр дополняется amount_rub IS NOT NULL, но исключение неизвестной суммы нужно раскрыть в отчете.

Запросы в упражнении читают данные. В рабочей системе даже чтение может создать нагрузку и раскрыть сведения. Не экспериментируйте на производственной базе без согласования. Для значений из пользовательского ввода используйте параметры драйвера, а не склеивание SQL; названия таблиц требуют отдельного контроля и параметрами значений не подставляются.

2. Агрегаты и смысл знаменателя

COUNT(*) считает строки результата, COUNT(amount_rub) — строки с непустой суммой. В paid-выборке три строки, но известная сумма есть у двух. SUM(amount_rub) дает 3000, игнорируя NULL; это сумма известных значений, не доказанная сумма всех оплаченных заказов. Пустая выборка для SUM дает NULL, а не автоматически ноль.

SELECT customer_id, COUNT(*) AS n, SUM(amount_rub) AS known_sum FROM orders WHERE status = 'paid' GROUP BY customer_id ORDER BY customer_id вернет (10, 2, 3000) и (30, 1, NULL). Для клиента 30 значение NULL сохраняет факт отсутствия известных сумм. COALESCE(..., 0) допустим как отдельное правило представления, но не превращает неизвестную сумму в достоверный ноль.

WHERE отбирает исходные строки до группировки, HAVING фильтрует уже полученные группы. Добавление HAVING COUNT(*) >= 2 оставит клиента 10. Если выбрать негруппированное поле без агрегата, SQLite допускает отдельные конструкции, но результат может не иметь нужного смысла; начинающему следует явно группировать все выбранные неагрегированные поля.

Среднее известных paid-сумм — 1500. Деление суммы 3000 на три paid-заказа даст 1000 и незаметно трактует неизвестный заказ как нулевой. В отчете нужны 3 заказа, 2 известные суммы, сумма известных 3000 и оговорка об одном пропуске.

3. JOIN и зерно таблицы

JOIN соединяет строки по условию. У каждого клиента может быть несколько заказов, а у заказа — несколько позиций. До соединения запишите зерно: одна строка orders — заказ, одна строка lines — позиция. Если одному заказу соответствуют две позиции, его поля появятся в двух строках соединенного результата.

В lines для заказа 1 заданы две позиции A и B, для заказа 2 одна C, для заказа 4 одна D. Сумма известного amount_rub после JOIN paid-заказов с позициями равна 4000: 1000 + 1000 + 2000. Исходная сумма известных paid-заказов — 3000. Число 4000 не означает рост продаж; заказ 1 посчитан дважды.

Если нужен итог по заказам, считайте его в orders или сначала сведите позиции до одной строки на заказ. SUM(DISTINCT amount_rub) не является общим исправлением: разные заказы могут иметь одинаковую сумму, и DISTINCT ошибочно объединит их значения. Уникальность определяется ключом, не совпадением суммы.

LEFT JOIN сохраняет строки левой таблицы без совпадений справа, дополняя их NULL. Но условие на правую таблицу в WHERE может исключить эти строки и изменить смысл результата. Проверяйте количество строк до и после JOIN, число уникальных ключей и пропуски соединения.

Самостоятельное задание

4. Проверка и воспроизводимость

Сначала предскажите результат на маленьком наборе вручную, затем выполните запрос и сравните. Проверяйте не только итог: количество строк, уникальные ключи, NULL, статусы, граничные значения и сортировку. Совпадение одного итога случайно возможно даже при ошибочном запросе.

Файл sql-lab.json содержит схему, вставки, запросы и ожидаемые строки. Команда python3 run-digital-labs.py запускает проверки локально с временной базой в памяти. Создающие таблицы команды относятся только к этой базе; не копируйте их в рабочую систему.

В записке к результату укажите смысл одной строки, фильтр, валюту, пропуски, диалект и ограничения. Для SQL разных СУБД могут отличаться функции, типы и работа с датами. Успех в SQLite не гарантирует совместимость с другим сервером.

Если сумма не совпала, локализуйте этап: исходная выборка → фильтр → соединение → группировка. Не добавляйте DISTINCT только ради красивого числа. Исправление должно соответствовать модели данных, а не маскировать ошибку.

Q1. Какие order_id попадут в paid-выборку?

Ответ, основание и объяснение

1, 2 и 4; для стабильного порядка нужен ORDER BY order_id.

Статус cancelled у заказа 3 исключает его.

Основание: собственный учебный кейс и урок 1, версия 0.13.0.

Q2. Как найти неизвестную сумму среди paid?

Ответ, основание и объяснение

SELECT order_id FROM orders WHERE status = 'paid' AND amount_rub IS NULL ORDER BY order_id; результат 4.

NULL проверяется IS NULL, не равенством = NULL.

Основание: собственный учебный кейс и урок 1, версия 0.13.0.

Q3. Чему равны COUNT(*), COUNT(amount_rub), SUM и AVG для paid?

Ответ, основание и объяснение

3; 2; 3000; 1500. Это агрегаты по известным значениям с отдельным счетом всех строк.

SUM и AVG не включают NULL; неизвестная сумма не стала нулем.

Основание: собственный учебный кейс и урок 2, версия 0.13.0.

Q4. Почему сумма после JOIN с позициями — 4000, а не 3000?

Ответ, основание и объяснение

У заказа 1 две позиции, поэтому его 1000 повторено дважды. Считать итог нужно на зерне заказа.

Соединение один-ко-многим размножает строки.

Основание: собственный учебный кейс и урок 3, версия 0.13.0.

Q5. Можно ли объявить 3000 полной суммой paid-заказов?

Ответ, основание и объяснение

Нет, это сумма известных значений; у одного paid-заказа сумма неизвестна.

Частично известные данные не подтверждают полный итог.

Основание: собственный учебный кейс и урок 4, версия 0.13.0.

Q6. Почему SUM(DISTINCT amount_rub) не универсально исправляет JOIN?

Ответ, основание и объяснение

Он удаляет одинаковые значения сумм, а не дубли ключей заказа. Разные заказы по 1000 должны учитываться оба.

Уникальность объекта определяется ключом.

Основание: собственный учебный кейс и урок 3, версия 0.13.0.
